## Candidate package boundary

`packages/github` contains pagination/response-classification helpers and a bounded read transport. REST collection is GET-only; GraphQL uses approved read operations. Neither grants credentials or exposes upstream issue/Project mutation methods. Pagination, origin, timeout and rate-limit controls are tested locally. Transport implementation does not establish live installation permissions or source coverage.

## Implemented public content policy (#108)

The accepted rendering subset is escaped plain text only. Source Markdown, raw HTML, avatars and remote/source SVG images are disabled rather than passed to a sanitizer or image proxy. React renders titles as text; API projection excludes raw bodies and emails. Evidence links allow only validated HTTPS GitHub artifact URLs without credentials or query strings. No source URL is fetched by the renderer or export service. Generated proof SVG is separate, bounded server-owned text/geometry, with no source markup, scripts, links or assets. CSV cells are quoted and formula-leading content is neutralized; tests cover control/format characters, quotes and multiline cells.

The Vite production build injects a CSP meta element ahead of executable content. Scripts, styles, fonts and API connections are same-origin; inline scripts/event handlers, images, embedded objects, frames, workers and base overrides are denied. There is no `unsafe-inline`, `unsafe-eval`, wildcard, data or blob exception. Adding Markdown, images, third-party assets or connections requires a separately reviewed policy change. Development HMR is outside this production policy.

Vite preview additionally sends CSP with `frame-ancestors 'none'`, `nosniff` and `no-referrer`. A deployed static host must serve the same `documentHeaders` from `apps/web/security-policy.ts`; meta CSP cannot enforce `frame-ancestors`. The embedded policy protects script/content handling even on a plain static host, but is not proof of deployed response headers or clickjacking protection. This change does not deploy a host or modify account/network security settings.

Verification is tied to the actual renderer and exports: `apps/web/test/evidence-render.test.mjs`, `apps/web/test/security-policy.test.ts`, `apps/web/browser/security-policy.spec.ts`, and service read/proof export tests. The browser test loads the built document, verifies the application renders, blocks injected inline script/event handlers and remote images/fetches, and checks response headers. Local test fixtures are synthetic; real hosting, source permission and operator acceptance remain separately tracked.

Policy references: [MDN CSP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy) and [Vite HTML transformation](https://vite.dev/guide/api-plugin.html#transformindexhtml).

## Source basis and limits

- GitHub REST pagination uses the response `Link` header to discover a next page: [REST pagination](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api).
- GitHub REST rate-limit guidance says to honor `Retry-After`, use `x-ratelimit-reset` when remaining quota is zero, and wait at least one minute when a secondary-limit response provides neither: [REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api) and [REST best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api).
- GitHub GraphQL connections require cursor pagination with `first`/`last` in the range 1–100, and resource-limited responses can contain partial data plus errors: [GraphQL pagination](https://docs.github.com/en/graphql/guides/using-pagination-in-the-graphql-api) and [GraphQL rate and query limits](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api).
- A 404 does not prove an object is absent: GitHub documents that a private resource can return 404 when the caller lacks access: [REST troubleshooting](https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api#404-not-found-for-an-existing-resource).

These sources describe documented API behavior. They do not prove the selected app permissions, event coverage, visibility transition behavior, actor attribution, payload timestamp coverage, or capability of a particular installation. Issue #41 acceptance still requires a real payload example for every enabled event family and an owner-reviewed permission probe. Unsupported and unprobed families remain disabled or explicitly unknown; they are never interpreted as zero activity.
