# Reviewed inputs and policy previews

Partial implementation evidence for #60, #115 and #122. This does not establish operator acceptance, verified real source capability or public launch approval.

The private pipeline consumes accepted evidence requests from its controls store only when the verified configuration contains a matching `recognitionBindings` entry: `category`, `scope`, `policyVersion`, `metricId`, `sourceMetricId`, `repositoryId` and `reviewerIds`. Generic recognition uses the acceptance clock. The [specialist contribution adapter](domain-recognition.md) additionally requires a current, immutable-revision-bound private evidence record and the registry's merge, acceptance, check or public-disclosure clock. The request owner, exact public artifact URL, source metric and repository identify one collected fact; ambiguous matches fail closed. Independent reviewer decisions must match exactly one controls audit entry. Neither public claim projections nor source payloads can authorize recognition. Collaborator attribution is not inferred from owner acceptance.

Raw facts stay unchanged. Recognized facts are recomputed from current private decisions after source normalization, never cached as permanent source facts. Withdrawal, appeal, rollback, suppression and removal or replacement of a relevant audit receipt change the private fingerprint; publication checks this fingerprint and historical reads fail closed until a current snapshot is confirmed. Private request text and acceptance receipt identifiers are not added to public evidence. A controls store is a trusted private boundary, not a bearer-token API.

Current-state collection observations select the latest observation at the cutoff for each repository, family and subject; tied differing revisions fail closed. Historical observed transitions retain their individual provenance. The selection changes the normalization cache signature.

Each GitHub collection read captures its repository, family, run identifier, cursor and limit before asynchronous work. Reusing the caller's request object cannot change the invocation's approved family, page selection, checkpoint identity or the repository invalidated after Project scope loss. The collector continues to recheck the host's live authorization callback throughout the read; capturing request inputs does not preserve revoked access. Synthetic adapter regressions cover this boundary without establishing real-source capability.

The GitHub collector qualifies source timestamps before converting them to stored instants, using the same calendar-valid UTC profile as the GitHub normalizer: explicit `Z`, whole seconds or one to three fractional digits. Impossible dates, missing timezones, alternate offsets and finer precision remain unqualified. An event's unsupported occurrence time stays unknown; a record with no usable source revision is rejected. The collector cannot manufacture a midnight time from a date alone, roll February 30 into March or truncate a later fractional instant into an earlier one. Valid whole-second and millisecond values retain their actual instant, and source payloads remain unchanged. Synthetic adapter regressions cover this boundary for #84; they do not establish real-source capability or expand the metric engine's supported timestamp precision.

Each publication atomically stores a private immutable frozen metric input alongside the snapshot. `previewPolicy({snapshotId, policy, operatorId})` requires the host's `authorizePolicyPreview` callback, runs old and proposed definitions on that exact input, and persists the comparison and both policies with integrity hashes. `approvePolicyComparison({comparisonId, operatorId, approvalReceipt, releaseNotes})` additionally requires `authorizePolicyRelease` and a configured `policyApproverIds` membership. Both preview and approval recheck current source access, configuration, recognition decisions and contributor/artifact suppression after asynchronous work; saved comparisons bind the current guard so withdrawn inputs cannot be approved later. It persists a reviewed release manifest with `publicEnabled:false`; it does not activate a configuration or repoint a snapshot head. Reversal requires another reviewed comparison/configuration. Source-tested configuration activation and the protected operational console remain separate acceptance gates.

## Replacing and reversing a reviewed definition

Activating an enabled policy reference in controls records the reviewed version and public notes URL. It does not install a new `MetricPolicy` in an already running pipeline: the current controls document is a restrictive overlay over the separately approved protected baseline. The host must supply the complete approved definition when it replaces that baseline.

A protected host can compose the existing interfaces in this order:

1. Call `previewPolicy` with the current immutable snapshot and complete proposed policy. Review the old/new inclusion, value and rank differences, their causes, the frozen dataset and cutoff, and both exact canonical policy signatures.
2. Obtain designated authorization through `approvePolicyComparison`. Preserve its durable receipt and release notes. This reviewed manifest still has `publicEnabled:false` and cannot move a snapshot head by itself.
3. Publish the reviewed notes through the host's notes publisher. Bind the exact public `policyLink` to the release receipt and notes. In the host's configuration source verifier, verify the persisted manifest, previous and target versions, complete target signature and notes binding before reporting the target metric as policy-approved and source-tested. A version in `approvedPolicyVersions` alone is not this source receipt.
4. Use the normal configuration proposal, source preview, independent operator approval and activation path. Preserve the resulting document digest, approval and source-test receipt. The proposer cannot approve their own configuration.
5. Revoke the old baseline's host approval and stop its runtime. Construct a separately approved replacement containing the actual target `MetricPolicy`, its `metrics.stableJSON(policy)` signature, the reviewed approval receipt and public notes URL. Start that runtime and publish through the existing source, configuration, SQL and private-confirmation checks. A new public snapshot exposes the actual policy version, signature hash and notes URL; the configuration reference cannot rewrite the older immutable snapshot.
6. To reverse the change, review the prior complete definition against the new frozen snapshot, obtain a new designated release receipt and reversal notes, and use the configuration rollback proposal and independent approval path. Explicitly replace the protected baseline again. Retain the intermediate snapshot, both release receipts and every historical policy identifier.

`apps/pipeline/test/policy-definition-rollout.test.mjs` exercises that composition with a change from ranked observed totals to the same unranked totals and then back to the original definition. It uses the actual policy review, controls configuration, SQL publication and public-read implementation, verifies unchanged frozen facts and the original stored document/hash, and reopens the private SQLite configuration history. Public uncertainty stays partial and its diagnostic strings remain sanitized; later collections may advance coverage timestamps without changing the restored arithmetic or ranks.

The test's host identities, source permissions, baseline approval set and external notes publisher are explicit synthetic fixtures. It is an automated integration check, not an OAuth journey, a public notes deployment, a real policy approval, a complete-history certification or an atomic cutover between independently running processes. A production host still owns those integrations and must not infer new authority from this synthetic example.

These private tables contain contribution evidence and must participate in the host's privacy, retention, backup and deletion policy. No automatic retention duration or production hosting is selected here. Synthetic tests verify the engineering boundary, not real review authority or policy approval.

Activated controls source grants constrain both collection and historical reads. The active repository must retain the baseline installation ID, slug and every configured collection family; every baseline Project ID must still be explicitly approved. Removing any grant blocks the stale runtime until an independently approved baseline matching the new scope replaces it. An unrelated source probe cannot restore removed permissions.
