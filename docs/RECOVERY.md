# Encrypted backup and recovery

`infra/recovery/backup.mjs` provides bounded AES-256-GCM backup envelopes containing a PostgreSQL dump, reviewed configuration, required policy versions and source watermarks. Every backup uses a new random nonce; metadata and database/payload digests are authenticated. Keys are supplied separately as 32-byte buffers and never appear in an envelope or receipt. Keep the encryption key outside the backup storage with approved rotation and recovery access.

Encryption captures the validated key in a private crypto key object before invoking payload serializers. Mutating the supplied key buffer or its backing memory during serialization cannot select a different encryption key for that backup.

Encryption copies the validated database bytes into a separate, unpooled allocation before serializing the other payload fields. The encoded dump and its authenticated digest both use that copy, so custom configuration, policy or watermark serializers cannot make them disagree by mutating the caller's buffer or its backing `ArrayBuffer`.

Required-state checks apply to the actual serialized payload as well as the caller's input. Configuration retains its object requirement, policy versions must remain a nonempty array, and watermarks must remain an object rather than an array. Authenticated reads enforce those same shapes before any restore callback, including older envelopes whose serializers omitted a required field. Valid custom serializers run once and their serialized values are retained.

`writeBackup` captures the serialized encrypted envelope before awaiting filesystem operations, creates a private temporary file and atomically links it into place without replacing an existing recovery point. Its success receipt takes the dump digest and retention timestamps from those exact serialized bytes, so later caller mutations cannot change the saved backup or its receipt. Use `.lbbackup` filenames. `expireBackups(directory, {now, key})` authenticates regular backup files and removes expired files with a deletion receipt. Unrelated filenames and symbolic links are excluded. This local storage mechanism must be mapped to the selected host's encrypted offsite storage and accepted retention policy before deployment.

`readBackup` and expiry read through one opened descriptor and enforce the 192 MiB encoded-file limit on the bytes consumed, including growth after the initial size check. They inspect at most one byte beyond the limit and reject overflow before text decoding or JSON parsing. Before deleting an expired file, expiry verifies that its pathname still names the same regular file with unchanged size and modification metadata; an observed replacement or change is retained and reported as an error. This final check is not an atomic concurrent-deletion guarantee: backup storage must remain exclusive during expiry because a pathname can still change between that check and unlink. Direct reads continue to follow symbolic links, while expiry continues to skip symbolic links in its initial directory listing.

`restoreBackup` validates all required restore/suppression callbacks, serializable expected state and observation clocks before mutation. Future source cutoffs are rejected rather than reported as measured recovery evidence. Expiry-bypass reads still require a valid observation clock. It authenticates and decodes the selected backup before invoking expected-state serializers, so those serializers cannot replace the selected envelope or key. It copies the authenticated dump into a private unpooled buffer before expected-state serialization, so mutating the caller's shared backing memory cannot change the bytes passed to the restore callback. An invalid selected backup is rejected before expected-state serialization. It checks the target is empty through an injected database assertion, invokes the database restore transaction, reapplies current suppression/tombstone policy before inspecting restored state, and compares the actual snapshot/correction state against an expected state. The inspected state's canonical serialization is captured once for both the equality check and the receipt digest, including inspection results with custom JSON serialization. The restored database remains isolated until source watermarks are reconciled and privacy/cache policy has been revalidated. Restoring old backups must never republish a deleted or opted-out contributor. An external cache purge/publication adapter must be verified for the selected host.

The restore receipt measures operation milliseconds and the source window needing reconciliation. It records zero loss relative to the verified backup snapshot; post-backup data loss stays unknown until real source reconciliation. A timestamp gap is not a fabricated data-loss measurement. No RTO, RPO, retention duration, operator, alert destination or production-readiness promise is implied.

Run unit checks with `node --test infra/recovery/test/backup.test.mjs`. A real PostgreSQL drill is available with `RECOVERY_TEST_CONTAINER` naming an existing dedicated `leaderboard-task-*` PostgreSQL container containing the local synthetic `leaderboard` user: `node --test infra/recovery/test/postgres.test.mjs`. The drill creates and removes only uniquely named `_test` databases. It dumps a known synthetic snapshot/correction state, restores into an empty database, reapplies a newer suppression and inspects the resulting actual SQL state. It prints a sanitized measured receipt. This proves backup mechanics with synthetic PostgreSQL data; staging DNS/TLS, deployed runtime snapshots, source reconciliation and accepted operations targets remain #103/#130/#131 acceptance work.

## Hosted synthetic validation

[Isolated encrypted PostgreSQL recovery](../.github/workflows/recovery-ci.yml) runs the existing recovery unit tests and real PostgreSQL drill on every pull request and main push. It uses a fresh GitHub-hosted runner, read-only repository permissions, pinned actions and no repository secrets or production data. The official `postgres:17-alpine` image runs under a unique `leaderboard-task-recovery-<run-id>-<attempt>` name, preserving the drill's existing target guard. The container has no network access or published ports; PostgreSQL is reached only through `docker exec`. Its data is temporary, with a 256 MiB data mount, 512 MiB memory limit and one CPU.

The job is capped at ten minutes, with separate startup, test, cleanup and artifact-upload limits. Readiness retries are bounded. The test step fails on skipped cases as well as test failures, so missing `RECOVERY_TEST_CONTAINER` cannot silently turn this check green. An unconditional cleanup step removes only this run's named container and volumes, including after test failure; the disposable hosted runner is the final isolation boundary if a job is forcibly terminated. No shared service, database or Docker resource is pruned.

The `synthetic-recovery-evidence` artifact retains only the TAP report and its sanitized `restore-drill-receipt/v1` output for seven days. Dumps, encryption keys and backup envelopes are not uploaded. The receipt measures restore execution and verifies the synthetic snapshot, correction and reapplied suppression. Its zero source gap is a fixture property; it does not measure real post-backup loss or an accepted recovery objective.

Measured CI evidence is pending until this workflow runs on the reviewed commit. Record the exact commit and Actions run URL with its receipt before citing a successful hosted drill. Local unit and workflow-contract checks do not replace that execution when Docker is unavailable. This is partial validation for #103 and #130; approved RTO/RPO, owner sign-off, staging recovery/readback and production acceptance remain open.
