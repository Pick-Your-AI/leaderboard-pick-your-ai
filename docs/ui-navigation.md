# Navigation acceptance evidence

This record supports [LB-13.02 / #52](https://github.com/Pick-Your-AI/pick-your-ai-leaderboard/issues/52). It describes the navigation behavior and its executable checks. The prototype is explicitly synthetic; API browser tests pass synthetic provider inputs through the actual built service handler. Neither establishes a deployed source, participant result or permission grant.

## Displayed snapshots survive navigation

A real-handler browser replay against accepted main `90deab1aba84f479d1c1de04789f58db3e2b155d` reproduced two failures:

- A board displayed `api-1`, opened a contributor portfolio and then received a newer publication. Back loaded `api-2` because only portfolio/activity history entries retained the displayed snapshot.
- The primary Measures link retained the repository, Project/workstream, interval and actor selection but omitted the displayed snapshot. A subsequent catalog journey could select the newer publication.

The API reader now records the displayed pin for every successful page with snapshot metadata. Before leaving an implicitly selected page, it makes that existing history entry reproducible. Primary navigation and the wordmark use the displayed pin, including navigation into the separate wall application. Explicitly pinned URLs, proof parameters and drawer history markers already identify their view and remain intact. History stores the URL, never an API response or contributor record.

Holding a snapshot does not suspend current privacy checks. Existing revalidation, suppression, revocation and failure handling still apply. A user can deliberately clear the snapshot in the exact-scope form to request the current publication; a regression verifies that this advances to `api-2` while ordinary navigation stays on `api-1`.

## Reference scope and restored date controls

A further receiving check at accepted main `3e23673a04c8ba43ce59438e5abb8687e054ff36` found that the prototype catalog, methodology, coverage and other reference pages carried scope in their links but displayed neither the selection nor its invalid-parameter messages. The original board-focused journey assertions had not exercised those intermediate pages. A real browser also restored the earlier custom-date URL after Back while its date inputs still displayed the newer interval.

The initial three-case reproduction failed for those missing controls, missing alerts and stale input values. The correction reuses the shared scope controls on the catalog, methodology index/sheets/change history, coverage, program, correction history, prototype guide and not-found recovery page. Reference descriptions state how the selection travels and which content remains a registry, inventory or example view. They do not claim that changing scope filters the reference content or establishes source availability.

Custom date fields now synchronize when the applied period or interval changes, including Back and Forward. Editing an unapplied interval still requires **Apply dates**; unrelated scope changes do not discard that draft.

A separate source review found two further consistency gaps. Multiple accepted Project IDs could survive in the URL while the Program control showed only the first; it now identifies a multiple-selection link in the same way as Repository. Choosing a single Program explicitly replaces that selection, while unrelated changes, copied URLs and history preserve all selected IDs. Invalid or reversed custom bounds supplied alongside a valid named preset now use the documented last-30-days fallback, matching their visible explanation. Other scope selections remain intact, and valid custom bounds still take precedence over a preset. When a valid custom interval accompanies an unknown preset, its explanation identifies that interval as the window in use instead of promising a different fallback.

The focused cases also cover an unapplied custom-date draft across repository and snapshot changes before **Apply dates**, multiple Program selection visibility and restoration, and agreement between invalid-window messages, controls and outgoing links. The scope unit cases exercise malformed, incomplete, reversed and empty intervals across every supported preset, retain a valid custom-window control, and round-trip repeated/comma-separated repository and Project IDs.

[reference-scope.spec.ts](../apps/web/browser/reference-scope.spec.ts) covers the nine reference/recovery routes with an explicit custom interval, repository, Program, actor selection and immutable pin at 320px. It verifies visible control values, intentional snapshot changes and restoration, scoped outgoing links, invalid-value explanations before following defaults, and custom/preset date history on an existing board. Custom URLs use canonical `from`/`to` parameters; the date pair implies the custom period. UI mode is a separate selection and is not asserted as global scope. Existing keyboard, reflow and accessibility route checks continue to apply.

The expanded comparison ran all seven browser cases against accepted main `10c38188a77de55202bd66641a5dbb6218949202` with only the new test added, then against this correction. The baseline had six failures and one passing draft-preservation control; the corrected source passed all seven. The separate scope unit comparison had ten passes and two failures on the baseline, then all twelve passes with the correction. Both comparisons executed their individual assertions with no skipped cases.

The local browser comparison used Playwright 1.64.1 and the matching pinned Chrome for Testing 156.0.8078.4, installed from Google's official archive with an explicit executable path. These synthetic checks demonstrate the described navigation and control behavior; fresh configured hosted results are still required for the published candidate. The 320px captures show the actual viewport; assertions also check lower control values and scoped links outside that captured viewport.
