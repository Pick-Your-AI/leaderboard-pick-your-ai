The baseline release classes remain **19 automatic baseline, 21 conditional, 41 evidence-reviewed, 16 descriptive-only and 1 deferred advanced**. These classes describe prerequisites, not enabled capability or an installed permission. Raw observations and independently qualified outcomes remain separate even within one definition.

**Presentation key:** Observed means a precisely labeled activity view; Qualified means the stated artifact/outcome criteria and any required independent acceptance are satisfied; Reviewed means an accepted evidence-specific judgment; Context is unranked; Spotlight is optional unranked editorial/milestone presentation; Deferred is unavailable pending separately reviewed work. An Observed / Reviewed row needs separate clocks and labels for its proven event and receipt-based lenses. All are policy defaults **when supported**, not additional selectable API parameters or assertions that a source exists. Missing source, identity, timestamp, consent or acceptance retains the applicable unknown/unavailable state.

## Source limitations applying to every row

The [source capability matrix](source-capability-candidate.md), [coverage rules](METRICS.md#coverage), [research adapter](research-record-adapter.md) and [documentation/locale adapter](documentation-adapter.md) require actual approved source evidence. The historical organization inventory is not a current allowlist. Personal-token reads, mocks, successful validators and GraphQL schema documentation do not certify the actual App installation or fill missing history. Optional Discussions and Project subtypes need their own fresh capability evidence.

The following official documentation was checked on 2026-10-18 to retain concrete collection limits. The design consequences are this review's policy judgments; the checks did not install an App or run a live canary.

| Official source | Documented limit and decision consequence |
| --- | --- |
| [REST pull request files](https://docs.github.com/en/rest/pulls/pulls#list-pull-requests-files) | The file response is capped at 3,000 files. Exhausting its pages cannot certify a larger diff; use the existing bounded, pinned read-only Git path or preserve partial/unavailable source state. |
| [Public Events API](https://docs.github.com/en/rest/activity/events) | The feed is limited to 300 events within 30 days and can lag 30 seconds to 6 hours. It cannot establish historical completeness or a real-time contribution ledger. |
| [Failed webhook deliveries](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries) and [delivery inspection](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/viewing-webhook-deliveries) | Failed deliveries are not automatically redelivered, and delivery inspection covers the past three days. Durable ingestion and reconciliation must retain gaps until verified recovery; a quiet webhook is not zero work. |

Preserve the canonical rules that current Project fields/order/configuration, a current thread resolver, or an item's latest editor/assignee do not establish every past actor and timestamp. Prove the exact actor-bearing subtype or use separately labeled reviewed receipts; unavailable counterparts, deleted content and partial pages stay unknown. No source gap justifies new write, Administration, Members or private-security access for a scoreboard.

For a complete bounded result, every required source/repository and affected row must cover the selected interval without gaps, ambiguity or errors, and both its reconciled source watermark and snapshot cutoff must reach the exclusive end. Keep actual source precision. Pending recognition is not part of the accepted numerator; a zero or rank movement requires its own coverage conditions. The accepted [public participation contract](public-participation.md) demonstrates this distinction without claiming reviewed organization-wide origin.
