# Metric and recognition policy decision

Policy decision: `recognition-governance/v1`, for [LB-01.02 / issue #24](https://github.com/Pick-Your-AI/pick-your-ai-leaderboard/issues/24). The prerequisite is the [product journey decision](product-journeys.md). Review and merge of the linked policy PR record acceptance under the project owner's delegated engineering authority. This document defines the product's rules; it supplies no installed-source receipt, runtime role assignment, contributor consent or production activation.

Source admission, voluntary profile/external/editorial choices, suppression and retention follow the [evidence and contributor-rights policy](evidence-contributor-rights.md). This decision adds metric presentation, ranking and correction/version rules while preserving that policy's separation of received requests, public suppression, payload deletion, backup completion and copies outside the service's control.

The [definition review](metric-definition-review.md) covers all 98 definitions at registry contract `leaderboard-metrics/v1`, definition policy `candidate-0.1.1`. Each row links to its complete, revision-pinned definition and records the source limit that controls its interpretation. Their units, actors, clocks, counting rules, release classes and work-package mappings are preserved. The review is a policy/source-boundary review, not a claim that 98 adapters or 98 public boards exist.

## Decisions and rationale

### Independent boards and their defaults

There is no universal weighted contributor score in the initial release. Do not sum, average, normalize or weight unlike categories into a contributor total. A person can contribute through code, research, review, triage, documentation, design, accessibility, operations or community work without competing in every category. Profiles and the unranked directory provide the common discovery path required by journeys J1–J3.

Each metric has its own default evidence lens and source clock:

| Definition meaning | Default when its source and implementation are usable | Rationale |
| --- | --- | --- |
| Accepted or integrated artifact participation | Qualified, or reviewed where the definition requires independent evidence review | Recognition follows the stated artifact/outcome criteria. A submitted or merely observed item cannot enter the accepted numerator. |
| Directly observed activity, such as opening an issue, submitting a review or applying a label | Observed, labeled with the exact activity and unit | These are useful contributions to discover, but neither elapsed time nor a surviving label proves correctness, quality or acceptance. |
| A qualitative finding, reproduction, mentorship or other accepted evidence claim | Reviewed, with a current independent receipt bound to the exact artifact/version and category criteria | A file count, generic approval, merge, status or nomination cannot prove the claimed outcome. |
| A diagnostic, descriptive-only definition or context measure | Unranked context, with its denominator, sample and limits | Ratios, wait times, net change and breadth do not create a merit, attendance or speed comparison. |
| An editorial definition | Optional, consented, unranked selection with its rationale | A spotlight is an editorial choice, not an earned numerical rank or an endorsement inferred from activity. |
| An unavailable source or deferred definition | Discoverable method with an unavailable/deferred state | A missing implementation, unproven source or absent permission cannot become a zero or another metric. |

The per-definition table specifies which rule applies; it is a presentation decision, not a list of enabled runtime policies. Raw and accepted views remain separately inspectable when implemented. Never fall back from an unavailable qualified/reviewed choice to a raw value under the same label, combine states, or invent an acceptance time for an observed action. Pending evidence is a separate count and proof path: 14 accepted plus 3 pending remains 14 accepted. A later qualification of the same policy unit replaces its pending representation without adding a second accepted unit.

At accepted main `88b0c43ee6ef962fb960ebd8e51a32d6d694ad23`, including locale #188 and specialist evidence #202, the candidate UI registry advertises **28 exact state/date pairs across 27 definitions**; 70 definitions remain definition-only and retained lines are deferred. The [dated capability inventory](metric-definition-review.md#candidate-support-at-the-accepted-implementation-refresh) preserves the original nine pairs and records the 19 added domain combinations. Seven original pairs have prototype adapters; `items_triaged` has engine/normalizer support and localization has its audited source integration. The domain combinations have source-to-qualification-to-engine verification, while the prototype rejects domain-only combinations. These are candidate capabilities, not live-source acceptance or public enablement.

The [UI registry](../packages/metrics/UI_REGISTRY.md) requires each consumer to check its own adapter. The presentation term Reviewed denotes an evidence-specific judgment; the accepted [domain adapters](domain-recognition.md) encode their independently reviewed outcomes using the `qualified` state. Fifteen use `acceptedAt`; documentation and tests use source merge time, freshness checks use check time, and security uses public disclosure time through `occurredAt`. Documentation keeps its separate `qualified/acceptedAt` prototype default. The prototype `decision_records` pair uses `reviewed/acceptedAt`, whereas the [research adapter](research-record-adapter.md) requires the definition's merge clock through `occurredAt`. Locale likewise retains source merge time when qualification arrives later. A production policy must honor these adapter boundaries. This decision changes no candidate pair or implementation.

Overview and wall categories may use the supported examples already declared by the registry, with their observed/qualified/reviewed labels visible. Raw issue, review and triage examples must remain labeled activity. Lines are an optional volume lens with equal access to the other contribution categories; they do not determine a homepage winner. A specialist or reviewed-evidence selection requires its corresponding source adapter, actual reviewed source evidence and approved release manifest; it need not wait for all 98 definitions to become available.

### Time, ranking and coverage

The product default is the last 30 days in UTC, with explicit half-open bounds `[start,end)`. Keep the existing supported 7/30/90-day, calendar and custom choices. The public read API serves exact materialized selections; an omitted API date currently means its materialized all-time scope. Clients must request the intended supported window explicitly and report it unavailable when no matching snapshot exists. They must not relabel an all-time result as a 30-day result. Event-time Project/workstream membership is the comparison default; current membership is a separately labeled lens.

Use the definition's actual clock: creation for opened work, a proven ready transition for readiness, merge/default-branch integration for those artifact measures, acceptance for receipt-defined outcomes, and the proven event time for triage. Source occurrence, independent acceptance, observation, collection, snapshot cutoff and publication remain separate facts. A later receipt can qualify work in its original merge period where the definition requires that clock; it cannot be backdated to invent an earlier review. Missing dates stay unknown. Compare instants using the source contract's precision, including equivalent offsets and sub-millisecond boundaries; do not silently round evidence into another window.

Independent count/sum boards use descending values and dense ranks: `12, 12, 9` receives `1, 1, 2`. Equal values share rank. Stable actor ID orders public ties for pagination; it does not confer a better rank. Unknown values have no numerical rank. The pure engine's internal login/ID ordering is not an additional merit rule. No negative points attach to removals, corrections, reversions or reopened work. A historical merge remains a fact, while currently effective work may have a separately labeled view.

All descriptive-only metrics, ratios, wait distributions and editorial selections are unranked. Preserve the source unit of net lines; the current nonnegative engine does not implement signed net aggregation. Set the initial descriptive reporting floor to **10 decided PRs** for `pr_accepted_rate` and **5 completed readiness-to-review samples** for `review_wait`, using the existing policy `minimumSamples` field. Below the floor, show the actual denominator/sample count and unavailable statistic, plus pending, missing-readiness and censored cases separately. These are conservative product display defaults, not statistical confidence thresholds. Counts/sums need no arbitrary tenure or minimum-count qualification; one eligible contribution can be discovered. Runtime configuration and source acceptance still precede use of these reporting defaults.

Coverage is an independent claim from qualification. A complete bounded result needs all required approved repositories and source families, enclosing gap-free coverage and known history start, exhausted pages, no unresolved source/permission errors, and no attribution/qualification ambiguity. **Both the reconciled source watermark and the selected snapshot's cutoff (`snapshot.generatedAt` in the public contract) must reach the exclusive end.** A row's narrower coverage must also satisfy the selection; a complete-looking snapshot cannot repair an incomplete row. This preserves the accepted [participation coverage rule](public-participation.md). Known positive partial counts can describe the observed subset with prominent limits; they do not establish complete organization totals. Within-snapshot ordering of that subset must say what was observed.

Zero requires complete relevant coverage and a genuinely zero measured result. Empty incomplete sources, missing dates, unavailable adapters and withheld aggregates remain unknown/unavailable, not zero. The roster does not create zero-valued people. A public Project containing hidden content cannot expose private item identities or inferred hidden counts. Current source/privacy checks apply to historical pins as well as current views.

Rank movement needs matching metric, evidence lens, definition, calculation-policy version/signature, filters, eligibility and comparable complete coverage in both snapshots. Fixed windows must match; rolling windows must have the same duration and valid cutoffs; calendar windows must be in the same relevant calendar period. New entrants have no invented former rank. Changed attribution, retained-evidence revision, backfill, withdrawal, unavailable source watermark or cutoff, or an incompatible period makes movement unavailable with a truthful reason. A privacy change must not reveal the identity or hidden reason behind a change.

### Participation, attribution and grouping

Eligible public contribution evidence can belong to an external contributor or an organization member, and can exist outside a Project. Organization membership, assignment, a mention, an account roster or an open task alone is not contribution evidence. Stable provider account/object IDs establish identity; current usernames are display aliases. Do not join people by name or email, expose commit emails, assign an unknown actor to a likely maintainer, or infer effort or AI use from account type or writing style.

Use the existing user-account view by default, with automation and all-account lenses explicitly available where supported. User-account activity may be automated; it is not a claim of manual work. Preserve reviewed service-account classification, bots, execution-mode evidence and unknown states. Respect definition-specific exclusions such as nonself, nonbot PR reviews and the existing automated-execution exclusion for candidate achievements. The same action can remain discoverable even when it does not satisfy an optional achievement rule.

Keep author, coauthor, reviewer, merger, triager, resolver, reporter, nominator and assignee distinct. Shared artifacts can show each verified participant's role once per defined unit. Display attribution does not estimate fractional labor, exclusive personal line ownership or duplicated organization delivery. Model trailers are assistance metadata, not human accounts. Different category/role counts may overlap and must not be summed into a contributor score.

Deduplicate source observations using authoritative identities and reviewed canonical lineage; webhook, REST and GraphQL observations of one action are one fact. Conflicting identities, revisions or quantities stay unresolved. Imports, mirrors, old transferred history, initial plan generation and setup campaigns remain explicitly separate from new delivered work. Unknown organization-adoption boundaries exclude ambiguous history from organization-specific comparisons; they do not erase a separately labeled inherited-history record.

For `items_triaged`, adopt the existing `triage-raw-state/v1`: stable actor/item/exact raw state in fixed 3,600-second UTC buckets from the Unix epoch. This is an observed grouping, not a semantic quality judgment. Preserve each other definition's distinct day, relation, artifact or change-set unit; do not apply that hourly rule to every triage measure. Group label/assignment/relationship toggles as their definitions require. A raw later-hour observation or a batch of 100 field effects is not 100 independently accepted outcomes. There is no automatic 14-day label acceptance, waiting-period credit, repeated-toggle bonus or punitive fraud score.

LOC defaults count eligible additions and deletions once at verified final default-branch integration, retaining separate code, tests, docs, research and configuration classification. Generated/imported/vendor/binary/lock/formatting-only exclusions and shared lineage remain visible. PR opener, original author, coauthor and merger are not interchangeable. No percentage-improvement comparison spans unlike performance workloads. Source URLs, string count, assertions, file count, severity labels, reactions and stars do not establish qualitative merit.

First qualifying evidence means first in the proven scope and known history. The current public participation extension leaves organization-history/newcomer classification unknown; a recent collection time or the first page of a portfolio cannot make someone a newcomer. Calendar-week activity is descriptive, never hours worked, a required streak or an inactivity list. Employment evaluation, compensation and personal performance management remain outside this product.

## Correction and acceptance authority

The project owner's delegated engineering authority is sufficient to review and adopt this repository's policy decisions. A proposed owner-role label does not block local implementation or create a named assignment. It also does not authenticate a runtime role, replace an actual source observation, or override a receiving workstream's explicit evidence/acceptance requirement.

| Decision or action | Authority and evidence required |
| --- | --- |
| Change these product/metric rules | Reviewed repository change under the project owner's authority, with version, rationale, affected definitions and before/after examples. |
| Accept an upstream research, code, design or release outcome | The source's actual applicable reviewer/receiving authority and exact artifact criteria. A leaderboard moderator cannot close the upstream acceptance gate by relabeling an item. |
| Accept a recognition claim | A current server-authorized independent reviewer, approved runtime policy and public source evidence, bound to the exact request, decision, artifact/revision, canonical unit and any required consent. Submitters and collaborators cannot approve their own claim. |
| Appeal or roll back a claim decision | A qualified reviewer independent of the claimant and earlier decisions on that receipt, following the implemented conflict and version rules. Unavailable independent authority leaves it pending. |
| Correct an identity or apply a data/privacy change | The verified subject or the specifically authorized privacy/correction role, using the implemented operation and an auditable receipt. A stored pending request is not an applied correction. |
| Activate or expand a runtime policy/source | The authenticated configuration workflow, current source-verifier evidence and an independent operator approval bound to the proposal digest/revision. This document is not a substitute for that receipt. |

Use the existing [controls](contributor-controls.md) separation of private requests, evidence review, self suppression and configuration. Correction records retain a stable ID, affected unit/revision, reason, evidence, decision actor, version, effective date, status and supersession. Minimize protected details; public reasons must not expose a privacy requester or restricted source. Self suppression and current withdrawal operate through their implemented paths. Generic correction/identity forms remain pending until the specific downstream change and rebuild actually succeed.

Review accepted evidence at the exact revision and preserve the source's domain boundary. Research compatibility acceptance remains governed by research's central workflow; a merged proposal is not a deployed implementation, a native measurement, market validation or receiving adoption. A validator pass establishes structure only. An evidence claim amended after review, changed collaborator consent, revoked audit, altered source binding or unavailable source requires current re-evaluation before it can support public acceptance.

An upheld change must reach affected boards, profiles, evidence, exports, cards, live views and retained-history reads. Withhold or revoke an aggregate when it cannot be recomputed safely; do not subtract receipt counts from a ratio or multi-unit sum. Preserve lawful minimal audit lineage and immutable historical calculation identities while enforcing current privacy. Downloads already outside the service cannot be recalled. Do not advertise a response deadline, private fallback destination or operating roster until an actual operator accepts it.

## Versioning and publication

Keep these independent version domains explicit:

| Version | Meaning |
| --- | --- |
| `recognition-governance/v1` | This reviewed product decision and the attached 98-definition source review. |
| `leaderboard-metrics/v1` / `candidate-0.1.1` | Registry contract and the reviewed definition snapshot; the candidate name is not renamed into a source or release approval. |
| Metric calculation policy version and signature | Exact evidence class, source clock, source set, grouping, thresholds, roles, eligibility and arithmetic for one metric. |
| Classification/grouping/identity versions | The specific source interpretation, lineage and attribution rules used by that calculation. |
| Snapshot ID/revision, computation version and source cutoff | The immutable materialized result and the evidence it could know. |
| Current publication-control version | Present privacy, suppression, source access and policy restrictions; never replaced by an old snapshot's controls. |

Every public metric must reach `/methodology/:metric` from discovery or its board, show the loaded definition-policy version and complete definition, and identify the selected calculation policy/version/signature and its reviewed public source when supplied. The existing [method renderer](../apps/web/src/remote/MethodDefinition.tsx) presents nested denominators, clocks, facets, permissions and acceptance examples; [registry discovery](../packages/metrics/UI_REGISTRY.md) includes all 98 methods without requiring a materialized board. The service rejects an unknown historical definition version instead of substituting the current meaning. A missing optional policy link is stated as missing and cannot satisfy a release's policy-provenance gate. Published configuration must supply its reviewed immutable GitHub policy link.

A semantic change requires a new version; reusing a version for changed rules is invalid even when the resulting totals happen to match. Compare old and proposed policies against the same frozen, currently authorized input. Review inclusion/exclusion causes, quantities, ranks and historical impact, publish minimized release notes, and retain the prior version for a tested rollback. Activation uses current authorization, source proof and compare-and-swap revision checks. Corrections create a new result revision; they do not edit an old snapshot in place or present recalculation as newly performed work. [Private comparison](private-policy-comparison.md) is a review aid and supplies no activation authority.
