# Independent metric engine candidate

`packages/metrics/src/engine.ts` implements the backend calculation boundary for [LB 11.01](https://github.com/Pick-Your-AI/pick-your-ai-leaderboard/issues/83), [LB 11.02](https://github.com/Pick-Your-AI/pick-your-ai-leaderboard/issues/91), [LB 11.03](https://github.com/Pick-Your-AI/pick-your-ai-leaderboard/issues/97), [LB 11.04](https://github.com/Pick-Your-AI/pick-your-ai-leaderboard/issues/98), [LB 11.05](https://github.com/Pick-Your-AI/pick-your-ai-leaderboard/issues/109) and [LB 11.06](https://github.com/Pick-Your-AI/pick-your-ai-leaderboard/issues/115). It is reusable calculation code, not a deployed service or an approved metric policy. All 98 registry definitions remain unchanged. Every aggregate and release manifest has `publicEnabled: false`.

## Inputs and policy boundary

`aggregateMetric(frozenInput, policy, scope)` consumes normalized `MetricFact` values with stable source-action keys, stable actor IDs, role, repository, source times, evidence state, artifact identity, and separately supplied event/current Project and workstream context. It does not infer stable IDs, acceptance, source capability, LOC exclusions, subject authorship, Project membership or identity from names. Collectors and metric-specific normalizers must establish those facts. `quantity` is the metric normalizer's eligible quantity, not arbitrary raw LOC; source/docs/tests/generated/vendor/lockfile classification and default-branch integration belong upstream.

Policies explicitly declare metric and definition versions, the registry unit, one evidence class, grouping, sources, role eligibility, date basis, sample threshold and whether the metric may rank. Aggregation must match the registry definition: count units cannot become arbitrary quantity sums. Signed net-change aggregation is explicitly unsupported by this nonnegative engine. No default policy is installed and no registry metric becomes enabled. Ratios and durations, and every registry `descriptive-only` metric, refuse personal ranking. Policy signatures prevent semantically different policies with the same version from becoming compatible movement comparisons; recalculation rejects changing semantics without a new version.

Qualified/reviewed facts require a nonempty acceptance receipt, a different accepting actor and a known acceptance time. Self-review against a known subject author is excluded. A receipt string is a reference to upstream reviewed evidence, not authentication or verification performed by this package. Authorized identity, acceptance and correction services must authenticate the evidence and resolve ambiguous subject attribution before release.

## Counting, replay and corrections

The engine selects each fact's latest reviewed revision observed by the frozen cutoff. Nonzero revisions without correction receipts and conflicting same-number revisions cannot silently replace an earlier fact. Original inputs are never mutated. Explicit canonical keys join duplicate adapter observations only when semantic facts agree; conflicting actor/action facts stay ambiguous. Source keys are required: missing identity cannot become a guessed event.

Policies can count canonical actions, one actor/artifact participation, or distinct actor/artifact/literal-state/UTC-interval groups. The last mode requires an explicit positive interval; no unreviewed triage interval or semantic state classifier is selected. Qualified work takes precedence over pending evidence for the same policy unit. Repeated policy units produce internal review receipts; they never produce public accusations. A later reviewed exclusion reverses the affected calculation when the immutable dataset is replayed, including historical cutoffs.

Count/sum rows carry evidence IDs, effective/observation times, unit, definition version, sample count, value state and pending count. Pending never enters the ranked numerator. Count, sum, ratio and duration are separate operations; there is no overall score or weighted combination. Missing sum quantities stay unknown. Numeric inputs and totals must be finite and nonnegative. Internal `audit` entries record inclusion and exclusion reasons and may contain suppressed fact/actor IDs: they require authorized access and must not be serialized as public API responses. Public-facing actor rows exclude suppression everywhere and neutralize deleted account logins.

Required pipeline persistence is documented in [Required private aggregate explanations](required-aggregate-explanations.md). It is independent of optional preview retention/capacity, and blocks publication confirmation when exact arithmetic/audit storage fails. Nonselected evidence classes, future observations and unknown ratio outcomes have explicit audit reasons.

## Scope and coverage

`resolveMetricWindow` defaults to 30 days and supports 7/30/90-day rolling windows, all-time, calendar month/quarter/year and explicit custom bounds. It emits exact UTC instants and a period label. Boundaries are half-open. Inputs with local offsets, invalid dates, reversed bounds or windows beyond the frozen cutoff fail. DST never changes the number of hours in a rolling UTC day.

Repository filters intersect the explicit allowed repository IDs. Project/workstream filters are independent lenses, unioning selected IDs within each dimension and intersecting dimensions. An event belonging to two selected Projects is selected once. `context: event` and `context: current` are distinct; unavailable membership remains unknown and is excluded from that filtered lens. Role, user-account, automation and all-actor filters remain explicit. A user-account event does not prove manual execution or the absence of AI assistance.

Complete coverage requires every requested allowed repository and every policy source to have complete, error-free coverage enclosing the entire window and a known history start no later than that window. Missing sources/repos, shortened watermarks, unknown/late history, gaps and ambiguous normalized facts prevent a complete result. Numeric zero is exposed only with complete coverage and no unknown evidence. Empty datasets do not invent zero-valued people. Unbounded all-time coverage is conservatively incomplete. Coverage intervals currently must be supplied as one enclosing record per source/repository; disjoint intervals are not silently joined.

For pending work on an acceptance-clock board, the separate pending column uses occurrence time because acceptance has not occurred. It is an observed pending cohort, not part of the decided or accepted denominator. Rebuilding a frozen input never substitutes ingestion time for a ranked metric's occurrence/acceptance clock.

## Ranking, diagnostics and participation

Ranks are dense, with equal values sharing rank. Codepoint login/ID order resolves display ties without changing rank. Movement requires matching metric, policy signature/version, definition version, filters and complete coverage. Exact fixed windows compare directly; named rolling presets compare only valid same-length bounds ending at their respective cutoffs, and calendar presets compare within the same calendar period. Custom windows do not receive inferred equivalence. Mixed policies, gaps, reversed snapshots and collector backfill revisions return explicit unavailable reasons. Newly added older effective evidence and removal of evidence still inside the new window also suppress movement, so historical import/correction cannot masquerade as fresh progress. Internal comparison signatures also suppress movement when a retained evidence ID changes actor, revision, effective time or measurement. Signatures contain no acceptance/correction receipts or source content and are not added to public API projections. Older aggregates without signatures return `insufficient_evidence_history`. Equivalent UTC timestamp spellings compare identically. New entrants have a separate state without an invented prior rank.

`pr_accepted_rate` counts merged / (merged + closed-unmerged), dated by decision time supplied as `acceptedAt`; closed-unmerged means a source decision, not evidence of accepted work. Pending remains separate and below-threshold denominators have no ratio. `review_wait` samples elapsed hours from evidenced readiness to first submitted review for the readiness cohort. It returns the sample values, n, median and nearest-rank p75, plus missing readiness and unresolved censoring. Reviews are observed through the frozen cutoff, including reviews after the cohort window ends. Missing readiness is disclosed separately and cannot enter a date-assigned duration sample. Neither diagnostic has a personal quality/speed rank.

`participationView` returns first qualifying evidence in organization history, observed/effective times, active UTC Monday-based weeks and the explicit number of weeks intersecting a bounded window. All-time has no invented denominator. Incomplete organization history, including unknown/ambiguous/conflicting normalization or unreviewed historic revisions, returns `newcomer: null`. A complete-known-history answer requires an explicitly reviewed origin and enclosing coverage for every allowed repository/source. Historical effective time, rather than a recent ingestion timestamp, determines newcomer inclusion. The result always states that first observed qualifying work is neither employment start nor proof of no earlier work. These descriptive views never normalize or change raw-count ranks.

## Policy comparison and release boundary

`comparePolicies` runs both versions on the same frozen input/scope and returns value, rank and included/excluded evidence differences, along with both complete audit trails and policy identifiers. Supplying the prior policy again deterministically reconstructs its prior candidate output; rollback does not overwrite historical identifiers.

`planPolicyRelease` requires a designated approver, receipt and release notes and constructs a version/signature transition manifest. The service must authenticate that actor, supply its protected approver allowlist, persist the manifest and release notes, perform a compare-and-swap policy transition, and retain rollback history. This pure function neither changes an active policy nor publishes release notes nor enables public metrics. The package does not provide a database lock, authorization server or deployment gate.
